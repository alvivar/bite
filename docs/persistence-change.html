Change guide · Persistence

A snapshot that is never half‑written

Commit ccc2edc changes how BITE writes data/db.bin and what it does when the file can't be trusted. Saves now go through a temporary file that replaces the old snapshot in one step. Damaged files and failed saves now stop the server with a clear error instead of silently losing data.

01

Where persistence sits

Clients never touch the disk. When the parser receives s key value it does two separate things. It queues the OK reply to the Writer, and it sends the value to the Data thread. Data inserts the value into a shared BTreeMap and raises a modified flag.

A separate DB thread runs a loop: it sleeps four seconds, then checks the flag. If the flag is set, it clears it and writes the whole map to disk. While the server runs, this is the only thread that writes to disk. The change affects this thread and the load at startup.

Worth rememberingOK has never meant "saved to disk", and it still doesn't. A change that isn't in the last snapshot that was successfully written can be lost if the process dies. There is no fixed time limit counted from the OK.

02

What could go wrong before

The previous code wrote the snapshot in place. It first opened db.bin with truncate(true), which empties the file immediately. Only then did it lock and serialize the map and write the new bytes. Until that write finished, the only copy on disk was empty or partial.

// src/db.rs before ccc2edc, save_to_file (abridged)
let file = OpenOptions::new() … .truncate(true).open(DB_FILE);
let data: Vec<u8> = bincode::serialize(&*self.data.lock().unwrap()).unwrap();
file.unwrap().write_all(&data[..]).unwrap();

// load_from_file
if let Ok(data) =
    bincode::deserialize::<BTreeMap<String, Vec<u8>>>(&content[..])
{
    *self.data.lock().unwrap() = data;
}   // on error: nothing, no log

The loader made it worse. If deserializing failed, it did nothing: no error, no log, and the server started with an empty map. The next change raised the dirty flag, and the next save wrote that small map over the damaged file. At that point nothing was left to recover.

03

The new save: build aside, then swap

save_to_file (db.rs lines 76–88) never opens the real snapshot for writing. It serializes the map while holding the lock, writes the full result to db.bin.tmp in the same directory, and flushes it to disk. Then fs::rename replaces db.bin with it. The old file is never deleted first; the rename replaces it directly.

// src/db.rs, lines 76–83 (long lines wrapped here)
pub fn save_to_file(&self) -> io::Result<()> {
    let data = bincode::serialize(&*self.data.lock().unwrap())
        .map_err(io::Error::other)?;

    let temp = self.dir.join(DB_TEMP_NAME);
    write_synced(&temp, &data)
        .map_err(|err| with_path(err, "could not write", &temp))?;

    let file = self.dir.join(DB_NAME);
    fs::rename(&temp, &file)
        .map_err(|err| with_path(err, "could not replace", &file))?;

Every step returns an io::Result. The small with_path helper (lines 98–100) keeps the original error kind and adds what was being done and to which path, e.g. could not write ./data/db.bin.tmp: ….

04

The new load: trust it or refuse it

load_from_file (db.rs lines 50–72) now separates nothing saved yet from something is wrong. The shared map is replaced in exactly one place, line 69, and only after the snapshot deserialized successfully. If anything fails, the map and the file are both left alone.

05

Failure is now a process decision

Returning errors is only half of it. Someone has to decide what an error means. The change puts that decision in main.rs and nowhere else: a persistence failure stops the whole process with a message. There is no global panic hook, and the other workers' unwrap() calls are unchanged.

06

What deliberately stays the same

This change is limited to how the snapshot is stored. Clients and existing data files notice no difference.

Wire protocol and commands
Same frames, same replies. OK is still sent before the value is saved.
Snapshot format
Still bincode of BTreeMap<String, Vec<u8>>. Existing db.bin files load as before.
Save timing
db.handle(4): the loop sleeps four seconds, then saves if the modified flag was raised.
Location
DB_PATH = "./data", file db.bin. The directory is now a parameter of DB::new, so tests can use their own directories.
Other threads
Reader, Writer, Parser, Subs, Cleaner and Heartbeat are unchanged.
Data thread
Still only inserts into the map and sets the flag; it never writes to disk.

08

What this does not promise

The goal is narrow: an interrupted save no longer breaks the snapshot, and errors are reported instead of hidden. Some limits remain:

  1. Recent changes can still be lost. If the process dies, any change that isn't in the last snapshot that was successfully written is lost, even if it was acknowledged. There is no fixed time limit counted from the OK.
  2. Not safe against power loss. The temporary file is flushed with sync_all, but the directory is not flushed after the rename, so after a power cut the rename itself may not have reached the disk.
  3. Linux is untested. Replacing an existing snapshot was tested on Windows only. Linux uses the same standard-library rename, but no Linux run was done. There is no platform-specific code.
  4. One server per data directory. The temporary file name is fixed, so two servers sharing ./data would overwrite each other's temporary file.
  5. A locked file stops the server. On Windows, if another program has db.bin open, the rename can fail. The server now exits with an error instead of corrupting the file.
